EasyEffects works fine in Flatpak (and everywhere) because it does not use module-pipe-tunnel or any FIFO/named pipe at all.
How EasyEffects does it correctly
EasyEffects creates native PipeWire virtual devices (a sink + a source) using PipeWire’s built-in support.null-audio-sink mechanism (via the adapter factory or by asking the PipeWire core to load the equivalent module).
These are proper first-class nodes in the PipeWire graph — exactly like a hardware sink or a module-null-sink you would create with pw-cli or in pipewire.conf.d/. No filesystem path, no /tmp/fifo_*, no pipe.filename property.
Because there is no external FIFO involved, there are zero sandboxing problems with Flatpak’s private /tmp or restricted filesystem view.
Key points from EasyEffects’ approach

It creates its virtual sink/source when it starts (and keeps them alive as long as the process runs — or with background permission in Flatpak).
It then uses PipeWire’s native linking + metadata APIs (and WirePlumber integration) to route streams:
“Process all output streams” → automatically moves matching streams to its virtual sink.

I already tried asking all the big AI models, even providing output and the source archives, but it didn’t help. This is a problem that’s too specific for a stochastic machine to solve, I guess.

But I’m very glad to say: I finally found the solution!

With some classic documentation reading, code comparison and googling (or DuckDuckGo-ing), I found the pretty hidden PipeWire docs about access control: PipeWire: Access Control

It was only these three lines I had to add/change:

pw_properties *props = pw_properties_new(nullptr, nullptr);
pw_properties_set(props, PW_KEY_MEDIA_CATEGORY, "Manager");
context = pw_context_new(pw_thread_loop_get_loop(thread_loop), props, 0);
