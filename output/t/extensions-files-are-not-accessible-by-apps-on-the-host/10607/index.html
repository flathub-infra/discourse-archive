Hi, I am packaging org.kicad.KiCad on flathub.

TL;DR: My question is: Is there a way to make an extension’s files accessible on the host? If not, it seems that it’s currently impossible to split the KiCad documentation out into a .Docs extension?

In detail:

Currently we include the HTML documentation in the main flatpak, which – as of today – is 118 MB of data for everyone to download with every new install:

$ flatpak run --command=sh org.kicad.KiCad
[📦 org.kicad.KiCad ~]$ du -hs /app/share/doc/kicad/
118M	/app/share/doc/kicad/

So, I was looking into splitting the HTML documentation off into a dedicated .Docs extension, which would be not installed by default. This seemed straight-forward after I learned about bundled extensions. So I went ahead and added a new .Docs extension to add-extensions, bundling /app/share/doc/kicad:

add-extensions:
  org.kicad.KiCad.Docs:
    version: stable
    directory: share/doc/kicad
    bundle: true
    autodelete: true
    no-autodownload: true

Running the newly built flatpak locally, by default the extension directory is empty, as expected:

$ flatpak run --user --command=sh org.kicad.KiCad
[📦 org.kicad.KiCad ~]$ ls -lh /app/share/doc/kicad/
total 0

And, after installing the .Docs extension, the above path contains the help subdirectory. Again, as expected:

$ flatpak install --user --reinstall --assumeyes "$(pwd)/.flatpak-builder/cache" org.kicad.KiCad.Docs

Great! So everything’s fine, let’s push and merge!

But, wait! The help file is now not opening in the host browser anymore as it used to do!? Literally nothing happens when you click on Help → Help from KiCad (or any of the other editors) with the .Docs extension installed.

Without the .Docs extension installed, KiCad detects the missing files and offers to open the online help instead. But with .Docs installed, nothing happens. The Help → Help (or any other help) menu entry seems to be dead.

So I checked what was going on here, and it seems to be that the files from extensions are not appearing on the host file system. With the .Docs extension installed (and the being accessible from within the flatpak, see above), the path on the host is empty:

$ ls -lh ~/.local/share/flatpak/app/org.kicad.KiCad/x86_64/stable/97c4601cfe60b3554deff34f40dbfb04297ad4c231b36891c8f68d6da7dfde6f/files/share/doc/kicad
total 0

Extensions are a kind of runtime & mounted at the correct path when the application is run via Flatpak.

The actual location on the host should be /var/lib/flatpak/runtime/org.kicad.KiCad.Docs/…. I don’t know if there’s an API to provide file location of the host.

Replying to #2

Thanks for the hint. At least I have found the files on the host fs now.

But, shouldn’t flatpak then hand this file path over to the app you are starting on the host? In case of KiCad (which uses wxWidgets), “opening a HTML help file” means “start a web browser to display this file:// URL”.

The file:// URL KiCad tries to open is file:///app/share/doc/kicad/help/en/kicad.html when you click on Help → Help from the KiCad project manager (i.e. “KiCad”). In the currently published flatpak, this URL gets correctly translated, or re-mapped, to the /var/lib/flatpak/app/... location on the host fs.

But using an extension, flatpak doesn’t seem to do this translation correctly (or at all?). Is this a bug that should be reported or is this by design? To me it feels like a bug.
