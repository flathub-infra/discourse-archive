Hi everyone,

I maintain three small open source Linux configurators for hardware that only ships Windows software:

  • 8BitDo Ultimate 2 controller: GitHub - MiguelSanzBr/8bitdo-ultimate2-linux: Open-source Linux configurator for the 8BitDo Ultimate 2 Wireless controller (CLI + GUI): remapping, sticks, triggers, gyro, LED rings, profiles · GitHub
  • GameSir Cyclone 2 controller: GitHub - MiguelSanzBr/gamesir-cyclone2-linux: Open-source Linux configurator for the GameSir Cyclone 2 controller (CLI + GUI) · GitHub
  • ATTACK SHARK X11 mouse: GitHub - MiguelSanzBr/attackshark-x11-linux: Open-source Linux configurator for the ATTACK SHARK X11 wireless mouse: DPI, polling, buttons, lighting, battery (CLI + GUI) · GitHub

They’re Python + Tk, talk to the device directly over /dev/hidraw, have a CLI and a GUI, and are MIT licensed.

Before I spend time on a submission I want to be upfront: most of the code (reverse engineering of the official apps, the protocol, the GUI, the tests) and the packaging was generated with Claude. My part was testing every feature on the real hardware, the design decisions and reviewing the changes. I read the Generative AI policy, so I would write the Flathub manifest and the PR myself and disclose all of this in the form.

A few questions:

  1. With that much AI-generated code, is a submission worth it, or would it most likely be closed?
  2. The apps need --device=all (raw HID, no portal covers it) and a udev rule installed once on the host. Is that acceptable for this kind of tool?
  3. The projects are only a few days old. Should I wait for more history and real-world use before submitting?

For now they’re available as Flatpaks from my own signed repo: Miguel Sanz Flatpak repository

Thanks! (sorry my bad english)

No, these applications would not be accepted. Not only are they too young, but the AI usage is too high.

Even ignoring the dubious copyright situation and the massive environmental impact of AI, there is an quality issue with AI code.

Many who try to submit today on our platform only have vibe-coded AI code made in a few days. This poses many issues:

  • AI generation isn’t perfect. It’s code will include bad practices (as we often see with AI-generated manifests)
  • Many vibe-coder don’t have the necessary experience in understanding their own code. And probably never will, since using AI takes away the important process that allows you to build a skill in the first place.
  • Since the barrier to creating an application is very low, there’s often no investment in the software to maintain it. So we would just end with abandonware.

So we have to be very picky about allowing AI code if we want some amount of quality on Flathub. Your applications don’t hold the threshold now, and probably not later as well.

Apart from that:
Why are you creating separate applications for different devices? For mouses and keyboards, there has been an project to provide a unified method for configuring it with libratbag, with Piper as an frontend.

Vibe-coding an application isn’t the best solution. Contributing to existing projects can often be better.
